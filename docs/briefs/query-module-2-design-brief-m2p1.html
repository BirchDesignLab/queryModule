Design brief · Milestone 2, phase 1 · Oct 14, 2026

Query Module 2.0

A Query Module for the CAD suite where dispatchers and officers query state and national systems from one fast, accessible screen, read the answers where they ask, and where an implementer reshapes the screen without a code release.

The problemAnswers under time pressure, on every site's own terms

A dispatcher or officer asks a state or national system about a plate, a person, a driver's license or a piece of property, and has seconds to read the answer back over the radio. The first release did that, but the verdict on it was blunt: it works, and it reads as a developer tool. Every site also wants different fields, rules, commands and result layouts, and a code release per site is not workable.

The target is an operations console: dense, calm, dark-first, one clear accent, nothing decorative. The design holds to four goals. The answer is readable at a glance. A serious result is hard to miss. The screens are built to work by keyboard. And the people who run a site can change what the screen shows, see what dispatchers will see, and publish it.

Three rolesWho the screens are for

Dispatcher

DESK · 36 PX CONTROLS

  • Two panes: the query panel and Requests this shift
  • Quick access to the five common queries, Alt+1 to Alt+5
  • Form or one-line terminal command, one shared draft
  • Results read in place, in the request that asked

Officer

VEHICLE LAPTOP · 1024 x 768

  • One card at touch density, targets of 48 px or more
  • Large query tiles and a 64 px Run query
  • Night and red-shift themes one tap away
  • No muted text for anything that must be read; detail is one tap behind the summary

Implementer and administrator

BUILDER · NO JSON NEEDED

  • Shapes fields, rules, commands, result cards and keywords in plain language
  • Previews on the dispatcher's own screen, then publishes and can roll back
  • The implementer edits site configuration only
  • The administrator does the same and also manages users, roles and sessions

Design principlesEight rules every screen is held to

Configuration, not code

Fields, rules, commands, result cards and keywords are site configuration. A change is published, not released.

The preview is the live form

The builder previews with the same renderer dispatchers use. What the implementer sees is what goes live.

Accessible by design

Built for keyboard and screen reader use from the start, with a visible focus ring and body text at 7:1 contrast or better in every theme. Browser tests drive the main dispatcher and officer flows by keyboard, run an automated accessibility scan on the main screens, and check the query screen at 200% zoom and 320 px wide.

Night and red shift

Day, night and a red-shift mode that protects night vision. Each has its own focus ring and contrast proof.

Severity is never color alone

A serious result carries an icon, the word, a visible marker, a hidden spoken severity and a 4 px edge, as well as its color.

Read-back text in monospace

Plates, VINs, serial numbers, commands and reference IDs are set in a monospace face so they can be read back character by character.

One draft for form and terminal

A command echo under the form shows the terminal command being built. Switching modes keeps what was typed.

Focus is never lost

Incoming results, status changes and published config are built not to move focus or rebuild the control the user is on.

DirectionAn operations console

Four surface steps carry the hierarchy, so panels need few borders. One accent marks what is selected or actionable. Severity colors are reserved for responses and badges. The signature element is the command echo: under every query form a monospace strip shows the terminal command the form is building, live as the user types, with an Edit as command action. It teaches the terminal syntax and makes the form and the terminal one thing.

Key flow 1Ask, acknowledge, watch each source answer

Run query records the request and answers at once with an acknowledgment: a row in Requests this shift with the send time and a short reference. Under it, one line per source reads pending, then settles on its own as that source answers. A slow or failed source never holds up another. The text carries the status; an icon is never the only signal, and a screen reader hears one summary after each change.

Key flow 2Results where they were asked: the result card

Each source that returns draws a card inside the request. The card is a view over the answer, configured by the site. The summary comes first and is short; Show detail opens the rest below it without moving the toggle. A serious word in the answer is marked, and a badge on the card, on the request and in the announcement carries the highest severity, even when the word sits in a row nobody opened.

When no card is set up for a result, the card says so and shows every field under its path in the answer, so nothing is hidden. A source that is pending, timed out, failed or not run is one status line with its reason in words, never a card. A nested query that was skipped says why in a sentence.

Key flow 3The same card on the vehicle laptop

The officer layout uses the same renderer at touch density. Summary values are 20 px monospace, labels are 16 px in the body color, touch targets are 48 px or more, and detail stays one tap behind the summary.

Key flow 4Nothing is lost when the connection is

Live status travels over a socket. Every event is also written to a per-user log, and the client remembers the last event it applied. After a drop or a reload it says where it was and the server replays what it missed. If it was away too long, the server says so and the client reloads the request list instead.

Key flow 5The builder: cards, keywords and Try a match

Implementers shape the result cards in the same builder that shapes the query forms: a tree on the left, an editor in the middle and a live preview on the right, with undo, Review and publish, history and roll back. A published change reaches open dispatcher screens within 15 seconds and redraws the cards already on screen, keeping what the user was typing.
