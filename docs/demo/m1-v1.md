# Demo runbook: Query Module M1 v1

A click path for each persona, with what to show, what to say, and what this phase does not do yet.
Every step was checked against `main` at `deba3ba` (10-03-26, after the admin config API, the admin
console publish, history and users, and the forced password change) by reading the code and the e2e
specs named in each section; nothing here is from memory of the design. Text only: no screenshots.

**Mock data only.** The prototype uses a mock data source with canned responses. It never connects to
real state or national systems and holds no real CJIS data. Plates start `ZZ-`, names are
`TESTERSON`, and every person, vehicle and property record is made up. Do not type real records.

## Before you start

- **Accounts (by email).** `dispatcher@example.test`, `officer@example.test`,
  `admin@example.test` and, for the config-only path, `implementer@example.test`. The password for
  each is derived from the seed secret on the deploy host and printed once by the seed run (see the
  seed output).
  `scripts/ops/seed.ts` prints the `email / role / password` table once, to its own stdout; if it was
  not saved, see "Recovery" in [docs/demo.md](../demo.md). Never paste a password into chat, a ticket
  or this file.
- **Browser.** A desktop Chromium-class browser, about 1366 x 768. The officer account opens the
  mobile-unit layout on a desktop browser, because that account has a stored `mobileUnit` persona
  (spec 6.1: the stored persona beats the device guess). The dispatcher has none and gets the
  dispatch layout.
- **Example queries** that run from both the form and the terminal are listed in
  [docs/demo.md](../demo.md) ("Example queries"); this runbook points at them rather than repeating
  them.
- **Sign in** with Email and Password, then "Sign in". Focus lands on the "Query Module" heading;
  the first Tab stop on every page is the skip link ("Skip to query").

## What this phase does and does not do

Say this up front; it is the honest edge of the demo.

| Not yet | Why | What you see instead |
|---|---|---|
| Source answers (response cards, hit highlighting, results) | Dispatch to the mock sources lands in M2 (P0.5). | A submit ends at the server's acknowledgment (HTTP 202). The row in "Requests this shift" says "Acknowledged", the send time and a short reference. |
| Per-source status and a connection pill | Not part of this phase. | Nothing; do not look for them. |
| The Audit log in the admin console | The audit viewer is M2. | The entry reads "Arrives in M2" and is not clickable. |
| Server-side settings in the builder (auth, retention, role claims, source adapter settings) | The builder edits the client view of the config; those sections ride along unchanged. | The tree shows a note about server settings. |
| Real results for the "results" keyboard shortcuts | There are no results yet. | The shortcut sheet lists them, but they have nothing to act on until M2. |

## Dispatcher path: `dispatcher@example.test`

What this account shows: the dispatch layout (36 px controls), the query panel at `/`, and no Admin
link. Covered by e2e: `personas.spec.ts`, `retry.spec.ts`, `shortcuts.spec.ts`, `a1` to `a5`.

### 1. Quick access and subtype

1. **Do:** after sign in, look at the row of quick-access buttons: Vehicle, Person, Property, Wanted
   check, Driver's license. The hint under them reads "Alt+1 to Alt+5 pick a type".
   **Say:** "The five query types this site uses most are one click away, and each has a key."
2. **Do:** click Person, then Property.
   **Expect:** the panel heading changes to "Person query", then "Property query".
3. **Do:** on Property, use the Type control under the quick-access bar (Firearm, Boat, Article,
   Electronics, Vehicle). Pick Firearm, then Article.
   **Say:** "The subtype decides which fields are required: Firearm asks for make and caliber,
   Article asks for a description. That comes from configuration, not from code."
   **Expect:** required marks move as you switch (see the "Property, standard" row in
   [docs/demo.md](../demo.md)).

### 2. Form and terminal

1. **Do:** pick Vehicle. In Plate type `ZZ-0001`; State stays on its default. Press Enter.
   **Say:** "Enter sends it. There is no Run button to hunt for on a keyboard."
   **Expect:** a row in "Requests this shift": "Acknowledged", "Sent MM-DD-YY HH:mm:ss", a short
   reference with a copy button; one polite announcement "Vehicle query sent at ... Reference ...".
   **Phase limit:** the row stops at the acknowledgment. No result appears; that is M2.
2. **Do:** choose "Terminal mode" (or press Ctrl + `), type `VEH.ZZ-0001`, press Enter.
   **Say:** "Same query, typed the way dispatchers already work. The command mapping is site
   configuration too."
   **Expect:** a second acknowledged row for the same query.
3. **Do:** type `XYZ.1` in the terminal and press Enter.
   **Expect:** "Unrecognized command XYZ." in the "Command problems" list under the command line;
   nothing is sent.
4. **Do:** switch back to "Form mode" with the mode control.
   **Phase limit:** what moves between the two modes when you switch is still an open design
   question (spec open questions); do not promise a particular carry-over in the demo.

### 3. Retry on a failed request

A real failure is easiest to make by taking the API away while the page is open: stop the API
process (or container). The app gets a network error, not an HTTP error. (Blocking only
`/api/v1/queries` in the browser's developer tools also fails the submit, but `/api/v1/health` still
answers, so the "no connection" hold below clears by itself within a second or two; stopping the API
is the clearer demo.)

1. **Do:** with the API stopped, run `VEH.ZZ-0001` (form or terminal).
   **Expect:** a new row marked "Failed" with "The server did not answer."; "Run query" is held
   (aria-disabled, still focusable) with the visible reason "No connection to server", which is also
   announced. The app polls `/api/v1/health` (after a random delay of up to 1 s at first, doubling up to
   a 30 s ceiling), and Retry is gated while the connection is down.
2. **Do:** start the API again and wait for "Connection restored" (announced; the hold lifts).
3. **Do:** press Retry on the failed row.
   **Say:** "Retry sends the values the row kept, not whatever is in the form now. A request that got
   no answer is retried under the same idempotency key, so if the server did receive it, you get the
   original acknowledgment and the query does not run twice."
   **Expect:** a new "Acknowledged" row; the "Failed" row stays in the list; focus stays on the Retry
   button; one polite announcement "Vehicle query sent at ...".
4. **Note:** Retry does not appear for a rejected form (400), a forbidden query (403) or a changed
   site configuration (409): sending the same values again cannot help. A 503 shows "The server was
   restarting."; a 429 shows "Too many queries. Try again shortly."

### 4. Keyboard shortcuts

1. **Do:** press Shift + / (or open the account menu and choose "Keyboard shortcuts").
   **Expect:** a dialog titled "Keyboard shortcuts" lists every bound action. Esc closes it and focus
   returns to where it was.
2. **Do:** try the ones that work on this page, with focus outside a text field:
   `/` goes to the command line; Ctrl + ` switches form and terminal; Alt + 1 to Alt + 5 pick the
   quick-access types (Alt + 2 is Person); Ctrl + Enter submits; G then Q puts focus on the current
   quick-access button.
   **Say:** "Every binding is site configuration, so a site can change them; this is the default set."
3. **Phase limit:** Up and Down (select a result), Enter (show details), Delete (remove from view) and
   G then R (go to results) are in the list but act on results, which arrive in M2.
4. **Note:** a `/` typed inside a text field is text, not a shortcut.

## Admin path: `admin@example.test`

What this account shows: an "Admin" link in the header and the admin console at `/admin`, with two
sections in its left rail: "Site configuration" and "Users and roles". Covered by e2e:
`personas.spec.ts`, `visual.spec.ts` (parity blocks), `admin-config.spec.ts` (the core loop) and
`admin-users.spec.ts`; the builder editors by their unit tests. What the config means is in
[docs/site-config.md](../site-config.md); the routes are in [docs/api.md](../api.md).

### 1. Builder edit

1. **Do:** choose "Admin" in the header; the console opens on "Site configuration" (Form tab). The
   left tree lists "Query types" and the site settings; the search box is "Find a field or setting".
2. **Do:** select a query type, then a field, and change something small and visible, such as a
   field's label text, or add an item.
   **Say:** "This is the same configuration the dispatcher's panel is built from."
   **Expect:** the status line reads "Draft, based on version N" with a count such as "1 unpublished
   change."; error and warning counts appear if a change is not valid, with "Go to the first issue."

### 2. Same-renderer preview

1. **Do:** watch the "Live preview" beside the editor. Use "Preview as": Dispatcher and Officer.
   **Say:** "The preview is the real query panel, not a mock-up. Switch the view and you see the
   dispatch and the officer layouts of the same draft."
   **Expect:** "Same panel as the dispatcher sees. Queries are never sent from the preview." If the
   draft is invalid the preview pauses ("Preview paused: ...") and shows the last valid version.

### 3. Undo and redo

1. **Do:** press Undo (Ctrl + Z), then Redo (Ctrl + Shift + Z or Ctrl + Y).
   **Expect:** "Undone. Undo steps left: N." and "Redone. Redo steps left: N." When there is nothing
   to do the buttons stay focusable and say why ("Nothing to undo.").

### 4. The Changes view

1. **Do:** open the "Changes" tab.
   **Say:** "Before anyone publishes, this shows exactly what differs from the live version."
   **Expect:** "Changes from the live version", each difference marked Added, Removed, Changed or
   Reordered; with no edits it reads "No differences from the live version." The "Raw JSON" tab shows
   the same draft as text.

### 5. Publish and the open dispatcher form

The core loop of the demo. Start with the dispatcher signed in, with the query panel open, in a
second browser window. The dispatcher's page is never reloaded in this step.

1. **Do:** as the admin, make a visible change in the builder (for example add a field to Property,
   or make First name required for State `OK`), and check it in the "Live preview" first.
   **Say:** "The preview is the same panel the dispatcher uses, so what you see is what they get."
2. **Do:** choose "Review and publish". The dialog "Review and publish" lists "Changes to publish";
   choose "Publish version N".
   **Expect:** "Published version N. Dispatchers see it within 15 seconds." Publish is refused while
   the draft has any validation error: the builder says "Not published: N to fix first."
3. **Do:** switch to the dispatcher's window and wait, without touching the page.
   **Expect:** within about 15 seconds (the refresh runs every 15 seconds and on window focus) the
   open form picks up the new configuration. The new field or rule shows, what the dispatcher had
   typed and where their focus was are kept, and one polite message says "The form was updated by
   your administrator."
4. **Do (optional):** make the dispatcher's form stale on purpose (it must not have refetched yet),
   publish another change, then submit from the dispatcher.
   **Expect:** "The site configuration changed. Check the form and submit again." No Retry is
   offered; the form refetches the config.

### 6. History, export and roll back

1. **Do:** choose "History" in the builder toolbar. The "Version history" region lists versions,
   newest first: "Live" for the current one, "Previous" for older ones, with "Roll back" and "Export"
   on each.
   **Do:** choose "Export version N" to download `<siteId>-v<N>.json`, that version's own document.
   **Say:** "Every version can leave as a file, so config can go through a pull request and come
   back."
2. **Do:** choose "Roll back to version N" on a previous version and confirm the dialog "Roll back to
   version N?".
   **Expect:** "Published version M (roll back of version N)". Rolling back adds a new version; it
   never rewrites history. The dispatcher's open form goes back within about 15 seconds.
3. **Note:** a draft the admin had open now has an out-of-date base. Its next publish shows "A newer
   version was published" with "Load the latest"; choosing it asks "Load the latest version?" and
   "Discard and load" replaces the draft.

### 7. Users and roles (`admin@example.test` only)

1. **Do:** choose "Users and roles" in the console rail. The table "Users" lists each user with
   Name, Email, Role, Status, Last sign-in, Sign-ins, Distinct addresses and Actions.
   **Say:** "The sign-in figures are counts from the audit. The addresses themselves are never
   shown."
2. **Do:** choose "Create user", enter an email (use an `@example.test` address), a name and a role,
   then "Create".
   **Expect:** a dialog "Temporary password for NAME" shows the password once. Do not copy it into
   chat or a ticket. Choose "Done"; the password is nowhere on the page afterwards, and the new row
   reads "Must change password".
3. **Do:** in a private window, sign in as the new user with the temporary password.
   **Expect:** only a "Choose a new password" screen: no header, no Status page, no WebSocket. The
   same password is refused as the new one; a different one is accepted and the app opens.
   **Say:** "An admin never chooses or learns a user's password. The server makes a temporary one,
   it is shown once, and the user must replace it before anything else works."
4. **Do:** back as the admin, change the new user's role in the Role control, or choose "Disable
   NAME" and confirm.
   **Expect:** "NAME is disabled. 1 session ended." The user's open session ends and a new sign-in is
   refused. "Sign out everywhere" ends every session without disabling.
5. **Note:** you cannot change your own role or disable your own account, and the last enabled admin
   cannot be demoted or disabled ("At least one enabled admin must remain, and you cannot change your
   own role or account.").

## Implementer path: `implementer@example.test`

What this account shows: the Admin link and "Site configuration" only. There is no "Users and roles"
entry (a direct visit to `/admin/users` goes to Site configuration). The implementer can edit,
preview, publish, roll back and export config, and cannot submit a query (the API answers
`403 forbidden`). Run steps 1 to 6 of the admin path as this account.

## Status page: any account

Open "Status" in the header (`/status`). Covered by e2e: `status.spec.ts`, `visual.spec.ts`.

1. **Do:** choose "Status". Focus lands on the "Status" heading. Three ruled sections follow, each with
   a heading and, for the first two, a text chip (never colour alone): Connection, Configuration,
   Session.
   **Say:** "This is what the app itself can tell you about its health, using only what it already
   has."
2. **Connection:** the chip goes from "Checking" to "Connected" and the sentence reads "Connected.
   Heartbeat round trip N ms." (a live WebSocket hello, ping and pong), with "Last checked".
3. **Configuration:** the chip reads "Loaded", with the site name, a 12-character version hash, the
   schema version and when it was last checked. The published version number is not available to
   non-admin accounts, so the hash stands in for it.
4. **Session:** who you are signed in as, your role, and the layout ("Dispatch" or "Mobile unit").
5. **Do:** press "Check again".
   **Say:** "It re-checks both the connection and the configuration, on demand. Nothing polls."
   **Expect:** focus stays on the button; one polite announcement sums up the check, for example
   "Connected, configuration loaded".
6. **Do (optional):** stop the API and press "Check again". The Connection chip reads "Failed" in the
   error colour and the sentence gives the reason; the announcement says so.
7. **Phase limits:** there is no per-source status and no connection pill, and no App or build-version
   tile yet (both version numbers are still the placeholder `0.0.0`).

## If something goes wrong

| Symptom | Likely cause and fix |
|---|---|
| Sign-in fails for every account | Most likely the seeded password was not saved from the seed output; see "Recovery" in [docs/demo.md](../demo.md). |
| Sign-in is refused after several wrong passwords | Ten failed attempts on one account lock it for 15 minutes; one client address is also limited to 100 auth requests per 15 minutes (`packages/api/src/auth/rate-limit.ts`). Wait it out; do not keep retrying. |
| The officer account shows the dispatch layout | Its stored persona was not written by a part-failed seed run; see "Recovery" in [docs/demo.md](../demo.md). |
| A user created in the admin console can sign in but sees only "Choose a new password" | Expected: they hold a temporary password. They must choose a new one first; every other route answers `403 passwordChangeRequired`. |
| A publish does not reach an open dispatcher form | The form refetches every 15 seconds and on window focus; wait or focus the window. A form that has not refetched gets the "site configuration changed" message on submit. |
| A submit never acknowledges | Check the API is up (`/api/v1/health`); the panel shows "No connection to server" while it is not. |

## Deferred or not covered

Not on `main` and not shown here: dispatch to the mock sources and any source answer, the connection
pill and per-source status, the audit viewer, and results shortcuts that act on results (all M2 P0.5
or later, ADR-0012). Nothing here describes behaviour on an unmerged branch.
