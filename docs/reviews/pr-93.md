## Scope

The PR delivers:
- `MessageKeySchema` in `packages/core/src/contracts/primitives.ts`, with `MESSAGE_KEY_PATTERN = /^[a-z][A-Za-z0-9]*(?:\.[A-Za-z0-9]+)*$/` and `MESSAGE_KEY_MAX_LENGTH = 128`. It is lowerCamel segments separated by dots, linear-time, and keeps an explicit `min(1)` so the generated contracts keep `minLength: 1`.
- One shared bound on every message and label key carrier: config `labelKey` fields (server and the client allowlist), `ValidationError.key`, config diagnostic keys, and audit `key` and `params.labelKey`. A valid config therefore cannot fail an audit write on these keys (spec 5.2 step 4). Picklist codes, ids, paths and token names keep their existing schemas.
- Regenerated OpenAPI and site-config JSON Schema. The change is additive at key level (`pattern` and `maxLength` only).
- ADR-0005 gains a dated "Amended 09-26-26 (#61)" line in Consequences.
- Tests: the pattern and its timing; parity across every labelKey carrier in the server and client JSON Schemas; a site-level JSON-pointer error for a bad nested labelKey.

## Answers to the controller's questions

1. Linear time, cap and query data: the pattern is linear. Every repeated group starts with a literal dot, which the segment class cannot match, so each input has exactly one parse. The 128 cap fits every shipped key (longest 35). The pattern rejects spaces, hyphens, apostrophes, slashes and underscores, so plate- or name-shaped text such as `ZZ-0001` cannot enter an audit row. Alphanumeric fragments are limited by shape, not provenance: keys come only from code literals and config.
2. Same keys on every carrier: yes. One schema object is imported by config (server and client), validation errors, diagnostics and audit. No carrier is missed in current code, and no code, id or path is wrongly bounded.
3. Emitted keys inside the pattern: yes. Every diagnostic key is a string literal, the zod issue code travels in `params`, and all shipped config and locale keys comply.
4. Generated contracts: additive at key level. oasdiff reports a `response-property-one-of-added` false positive on inline `oneOf` members. The PR carries `api-breaking` (spec 9.3 step 7), #69 tracks named components, and the M0 release notes must list this PR.
5. ADR-0005 amendment: after the fix, it is a single dated Amended line in Consequences with the correct pattern. That is consistent with Lifecycle 4 and the W2 and W4 amendments.
