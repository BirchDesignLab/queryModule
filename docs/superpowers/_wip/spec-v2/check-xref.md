## Issues

- D001 must-fix 5.5/5.7 `credential_delegation` is defined twice with conflicting DDL: 5.5 describes one flat table ("one row per source", columns include `source_id`, `revoked_at`, `revoked_by`, `revoke_reason`, `requested_at`, status enum including `requestExpired`); 5.7 describes a parent `credential_delegation` (no `source_id`; columns `id`, `purpose`, `trainee_user_id`, `session_id`, `officer_user_id`, `code_hash`, status `pending|active|expired|revoked`, `requested_minutes`, `created_at`, `approved_at`, `expires_at`, `ended_at`, `end_reason`) plus a separate `credential_delegation_source` child table carrying the partial unique index. Fix: pick one design (the writer notes for 5.7 point at the parent+child model as intended) and rewrite 5.5's table entry to match it column-for-column, including the `requestExpired` status value.
- D002 must-fix 4.7/5.7/8.7 the lost-key reason value is spelled two ways for the same concept: 4.7's `credentialsDeleted`/`credentialsInvalidated` detail schemas enumerate reason `lostKey`, while 5.7's key-custody paragraph and both `scripts/ops/lost-key.ts` and `lost-data-key.ts` runbook write-ups (8.7) use `keyLost` throughout. Separately, 4.7's `delegationRevoked` reason enum (`trainee|officer|admin|sessionEnded|superseded|userDisabled`) has no lost-key value at all, though 5.7 and 8.7 both say a lost `CREDENTIAL_KEY` revokes active delegations with reason `keyLost`. Fix: standardize on one spelling (`keyLost` matches 2 of 3 sections) and add it to the `delegationRevoked` enum in 4.7.
- D003 must-fix 5.1/5.7 the delegation redeem/approve routes don't match: 5.1's route table has one row, `POST /api/v1/delegations/approve`, described as "redeems code, confirms or narrows sources and duration"; 5.7 describes two separate routes, step 3 `POST /api/v1/delegations/redeem { code }` and step 5 `POST /api/v1/delegations/:id/approve { sourceIds[], durationMinutes, totpCode? }`. Fix: add the missing `/api/v1/delegations/redeem` row to 5.1 and correct the approve row's path to include `:id`.
- D004 must-fix 4.7/5.3 the delegation WebSocket event is inconsistent: 4.7 defines one message type, `delegationChanged { delegationId, status: "pending"|"active"|"revoked"|"expired"|"requestExpired", viewerRole }`, covering every delegation transition; 5.3's event list instead names three separate types, "delegationApproved, delegationRevoked, delegationExpired", and never mentions `delegationChanged`, `delegationRequested` or `requestExpired`. Fix: make 5.3 reference the single `delegationChanged` type (matching 6.2's usage), or, if separate per-transition events are actually wanted, change 4.7 and 6.2 to match.
- D005 must-fix 4.7/5.3 the client-to-server WebSocket message names differ between the two sections that define them: 4.7 names `hello { lastSeq }` and `ackReceipt { correlationId, receivedAt }`; 5.3 names the same two messages `resume { lastSeq }` and `ackReceived { correlationId, receivedAt }`. Fix: use one name for each message in both sections (4.7 is the canonical contracts section).
- D006 must-fix 4.7/5.2 the `adminViewed` audit event's officer-read field is named and valued differently in the two sections: 4.7's schema is `{ correlationId, includeHidden, viewerBasis: "admin"|"delegationOwner" }`; 5.2's access-policy text says the delegating-officer read is audited "with `details.basis: "delegator"`" — different field name (`basis` vs `viewerBasis`) and different enum value (`delegator` vs `delegationOwner`). Fix: use `viewerBasis`/`delegationOwner` in both places.
- D007 must-fix 6.9/9/12.5 section 9 (CI) never builds or serves `apps/host-simulator`, but 6.9 and 12.5's M4 gate ("host-simulator Playwright test green") require it for the embedded-mode Playwright tests, and the lead's decision on `apps/host-simulator` explicitly calls for fixing section 9 alongside 3 and 6.9. Fix: add a CI step (9.3) that builds `apps/host-simulator` and serves it on its own origin next to the Docker image boot smoke, so the embedded Playwright suite has something to point at.
- D008 should-fix 4.1/5.6/6.9 6.9 says host roles "come from the claims map in `SiteConfig.auth`", while 4.1 and 5.6 both spell the full path `SiteConfig.auth.embedded.roleClaims`. Fix: spell out the full path in 6.9 to match (this exact gap was flagged in the writer notes as needing reconciliation at assembly and was missed).
- D009 should-fix structure sections 4 and 5 have no top-level `## 4 <name>` / `## 5 <name>` heading — the document jumps from `### 3.2` straight to `### 4.1`, and from `### 4.7` straight to `### 5.1` — unlike every other numbered top-level section (1, 2, 3, 6-14), which does have one. Fix: add the two missing top-level headings, or note that they're intentionally omitted and why.
- D010 should-fix 13 the current section 13 draft lists two IDs twice each: FR-065 (once as "Foreground only" M2/A6, once as "Background push partial, deferred" C5/later) and NFR-002 (once as "Multi-source and nested" B1/B2/M3, once as a bare volume/scale note).
