## Issues

- D001 must-fix §4.1/§4.5 `KeywordStyle` is defined twice with different shapes: §4.1 (schema section) declares `KeywordStyle { keyword, severity, except? }` with no per-keyword colour override, but §4.5 declares `KeywordStyle { keyword, severity, except?, style?: { color?, background?, bold? } }` and describes the renderer applying `style` to override colour/background/bold, plus a validation rule checking contrast on "each keyword style override." Since §4.1 says the server parses config strictly with unknown keys as errors, a site config setting `style` on a keyword would fail validation under the §4.1 schema while §4.5 depends on it existing and being checked. Fix: add `style?: { color?, background?, bold? }` to §4.1's canonical `KeywordStyle` (and its per-field contrast validation rule), or delete the per-keyword override entirely from §4.5 and its contrast-check sentence — decisions log c103 never asked for a per-keyword override, so deleting it from §4.5 is the smaller change.
- D002 should-fix §2/§4.1 c089's "conditional constraints deferred" is never stated anywhere in the draft — §2's non-goals list and §4.1's `FieldDef` constraints section are both silent on it. Fix: add a line to §2 non-goals (or a note under §4.1's string/number/date constraint fields) that constraints varying per rule condition are out of scope for the prototype.
- D003 should-fix §6.9 Fix #2 (host role-claims mapping lives at `SiteConfig.auth.embedded.roleClaims`) is applied correctly in §4.1 and §5.6 but not in §6.9, which says "Roles come from the claims map in `SiteConfig.auth`" — missing the `.embedded.roleClaims` part, so a reader of §6.9 alone gets the pre-fix spelling. Fix: change §6.9's sentence to name `SiteConfig.auth.embedded.roleClaims` explicitly.
- D004 should-fix §4.5 `ResponseMapping` is restated without the `id` field that §4.1's canonical schema declares (`ResponseMapping { id, queryType, sourceId?, persona?, when?, elements }`) and that §4.1's own Overlays paragraph relies on for merge-by-identity ("responseMappings by id"). §4.5's restatement drops `id`. Fix: either add `id` back to §4.5's restated type or note explicitly that §4.5 is showing an abbreviated view of the §4.1 schema.
- D005 should-fix §6.10/§11/§13 c006 and c015 say FR-071 should be cited in §11, §6.7 and §13, and the FR-065 background-push row should also cite §6.7 (in addition to being "partial, deferred"). The draft consistently cites §6.10 instead of §6.7 in all three places (§6.10's own "Covers" line, §11's decision table, §13's traceability rows for FR-071 and FR-065) with no note that §6.7 was renumbered/relocated to §6.10 during assembly. Fix: either restore the §6.7 citations or add a one-line note in §6.10 (or §13) that native/push content moved from §6.7 to §6.10 after the decisions log was written.
- D006 should-fix §9 Fix #4 (host simulator: `apps/host-simulator`, dev and CI only, never in the production image) is applied correctly in §3's package table and §6.9, but §9 (CI and repository process) never mentions building or serving `apps/host-simulator`, even though §6.9 says Playwright uses it for embedded-mode tests and §12.5's M4 gate is "host-simulator Playwright test green." Fix: add a step (or a line in 9.3) that builds/serves `apps/host-simulator` before the embedded-mode Playwright scenarios run.
- D007 note §5.5/§5.7 c052/c053's `credential_delegation` shape is marked open twice with two different answers on the table split. §5.5 lists one table, `credential_delegation`, with a comment "one row per source," and a partial unique index directly on it — this already matches c053's "partial unique index active (session_id, source_id)." §5.7 instead proposes splitting it into a parent `credential_delegation` plus a child `credential_delegation_source` table and flags "[open: child table shape; 5.5 owns the final DDL]." Recommend closing the open tag in favour of §5.5's single-table design, since §5.5 is the section the note itself says owns the final DDL, and dropping §5.7's two-table description removes the disagreement.
- D008 note §4.7/§5.2/§10.3 c070's officer/delegating-reader audit event is marked open in three places, but all three already independently converged on the same answer: reuse `adminViewed` with `details.basis: "delegator"` (§5.2) / `viewerBasis` (§4.7) / same test file in §10.3. Recommend simply closing the open tag by keeping `adminViewed` + a `basis`/`viewerBasis` field, and using one field name (`viewerBasis` per §4.7) in both places instead of two.
- D009 note §4.4 c093's "reject a date `outputFormat` containing the delimiter" and "reject a `decimal` field in a command position when the delimiter is `.`" are both marked `[open]` even though both rules are already fully specified and placed in the validation-errors list. Recommend closing both open tags as accepted rather than leaving them pending, since no alternative is offered anywhere else in the draft.
