### Task 5: Replay by `lastSeq` with caps and `resync` (spec 5.3)

**Files:** Modify `packages/api/src/dispatch/event-log.ts` (`eventsSince`), `packages/api/src/ws/server.ts` (on `hello`), create `packages/api/test/ws/replay.test.ts`; `docs/api.md` (replay section).
**Interfaces:**

```ts
export const REPLAY_MAX_EVENTS = 500;
// window: EVENT_LOG_RETENTION_MS (event-log.ts:22), no second constant
export async function eventsSince(db, userId: string, lastSeq: number, now: number):
  Promise<{ latestSeq: number } & ({ kind: "events"; events: WsEvent[] } | { kind: "resync"; reason: "tooOld" | "tooMany" | "unknownCursor" })>;
```

Rules (one read transaction gives `latestSeq` and the rows, so `welcome` and the replay agree):
- `lastSeq: null`: no replay (a fresh client; today's behaviour).
- `lastSeq` above `latestSeq`: `unknownCursor` (for example a reset database).
- `lastSeq` equal to `latestSeq`: nothing due, no `resync`, even when the newest row (kept by `pruneEventLog`) is older than 24 h.
- `lastSeq: 0`: the rows within 24 h (`ws.ts:19`: "0 replays everything within the caps"), or `tooMany` over 500.
- `lastSeq` above 0: `tooOld` when the lowest stored seq is above `lastSeq + 1` (pruned) or row `lastSeq + 1` is older than 24 h; `tooMany` when more than 500 rows are due; else the rows with `seq > lastSeq`, in `seq` order.

Message order on a socket: `welcome { latestSeq }`, then the replayed rows or one `resync`, then live events. Buffering starts at connect (today `ws/server.ts:121` sends live events as soon as the socket subscribes): live events are held until `hello` is answered, then flushed if `seq` is above the last replayed seq (or above `lastSeq`, or `latestSeq` when the replay is empty, `null` or `resync`); live events after a `resync` still flow. A second `hello` on the same socket is ignored (logged by id). A replay read failure closes the socket with 1011 (as `:131`). Each replayed row is re-validated with `WsEventSchema` before send. Owner rows only (`user_id` = the socket's session user). Track B Task 5 makes the client accept replayed seqs below `welcome.latestSeq` (today `feed-socket.ts:161` overwrites the mark on every `welcome`). Hidden results: no filter until `result_visibility` exists (M3 P2); a code comment says replay must skip hidden `sourceStatus` then (spec 5.3).
**IDs:** FR-043, FR-065, NFR-003; SEC-014; spec 4.7, 5.3, 6.8; ADR-0013.
**Tier:** critical (`dispatch/event-log.ts`) with gate (`ws/server.ts`).
