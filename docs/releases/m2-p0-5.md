# M2 P0.5 Dispatch

Date: 10-06-26

M2 P0.5 turns the M1 acknowledgment into a live dispatch (ADR-0012): a submit is queried against the mock sources in the background, each source settles once, and the outcome reaches the dispatcher's screen as live per-source status over the WebSocket. Results, mapping and severity are M2 P1. P0.5 is not a milestone exit, so there is no milestone tag; the demo pause point is M2 P1's gate.

## Config changes for site developers
Config schema stays at v1 and no site file changed. `pnpm config:validate --resolved` on `default.json` and `example-ok.json` prints the same resolved configs as the M1 release (the only difference from [`m1/default.resolved.txt`](m1/default.resolved.txt) and [`m1/example-ok.resolved.txt`](m1/example-ok.resolved.txt) is the `ok ...` status line the command prints first), so there is nothing to diff or merge:

```
ok packages/config/sites/default.json (6 warnings)
ok packages/config/sites/example-ok.json (7 warnings)
```

The warnings are the same `config.conditionallyRequiredWithoutPosition` set as in M1 (a field a rule can make required has no positional slot in the shown command). They do not fail validation.

What changed for a site developer or admin:

- Mock files (`packages/config/mock/default.json`, `example-ok.json`) are now read at runtime. The mock adapter answers from the stored mock of the config snapshot pinned to the request, not from the site file (#493). The files were regenerated by `scripts/mock-data/generate.ts <siteId>` and hold the same canned responses as M1 (the generator's output deep-equals the M1 files; only key order and formatting differ). Do not hand-edit them: `pnpm config:validate` fails on drift (`mock file drift: mock/<siteId>.json (run scripts/mock-data/generate.ts <siteId>)`).
- Fixture policy (spec 5.4, 10.8): every mock `respond` and `default` payload is checked against an allowlist of payload keys. Plates look like `ZZ-0000`, VINs are 17 VIN characters that fail the check digit, birth dates are real dates in 1901, names are synthetic (for example Testerson), addresses are `<n> Example Ave`, free text holds no run of four or more digits, and nested values sit only under container keys. A violation is reported by JSON pointer (`fixture.*` messages; never the value). `config:validate` runs it on each site's mock file. Trigger values (`when`) are inputs and are not checked.
- Admin console: validate, publish, rollback and draft save refuse a mock that breaks the fixture policy or the mock schema, and a draft that leaves a query type without a response on a mock source it asks (`config.missingMockResponse`) cannot be published. The builder gained a "Mock responses" tree node: a coverage grid (query types by mock source, gaps marked), a response editor (type-field match, default result, scenarios in order, response time per source), a changes view and an issues list. A new query type or new mock source gets a no-record scaffold in one step (CFG-2).
- Password minimum: `PASSWORD_MIN_LENGTH` (12, unchanged) in `packages/core/src/config/password.ts` is the single source for Better Auth and the change-password page; `password.change.tooShort` in `en.json` now takes `{min}` (SEC-005). Locale files gained `sourceStatus.*`, `fixture.*` and `admin.mock.*` keys; a site locale that overrides `password.change.tooShort` must use `{min}`.
- Mock scenarios the demo and the e2e use (`docs/demo.md` has the table): `ZZ-0001` both sources return, `ABC123` a clean no-record (story A4), `FAIL1` the state source fails while the national source returns, `TIMEOUT` the national source times out.

## Upgrade impact
- Migrations `0009` and `0010` (the API applies them at startup; take the usual backup first):
  - `0009_config_document_hash`: nullable `site_config_version.document_hash` (SHA-256 of the stored document's canonical JSON) and a recreated frozen-row trigger, so a set hash never changes or returns to NULL. Boot verifies the stored document by that hash, then applies the current schema's defaults and recomputes the served `configHash` (CFG-3): a schema addition with a default no longer refuses startup, a tampered row still does (`config.hashMismatch`). The first start after the upgrade backfills the hash of the published row, only after the row verifies under the old rule; otherwise it refuses to start. Publish and rollback compare version ids, so a recomputed hash never causes a permanent `draftConflict`. Prototype shortcut, ADR-0011 addendum; the proper fix (config schema version plus an audited migration of stored rows) is #558.
  - `0010_event_log`: `event_log` (per user, `seq` increasing within a user; `type`, `correlation_id`, `part_id`, `source_id`, `result_id`, `delegation_id`, `status`, `created_at`) with an index on `created_at`. It holds the `sourceStatus` events. Pruning keeps each user's newest row.
- First start sweep: before it listens, the server marks every `source_result` still `pending` as `interrupted` in one transaction, writes one `interrupted` audit row per row (system actor, reason `processRestart`) and one `sourceStatus` `event_log` row per swept row, under that row's owner. This is the M1 `pending` backlog (M1 submits never dispatched). Nothing is re-dispatched, a settled row is never rewritten, and a failed sweep refuses startup. A row left `pending` by a stop is swept at the next start in the same way.
- `ALLOW_MOCK_SOURCES` is unchanged: mock sources are still refused unless it is `true`, from the site file or a stored document, and `source_result.adapter_kind` records `mock`. The prototype never connects to a real state or national system.
- New optional deploy env: `WS_UPGRADE_LIMIT` and `WS_UPGRADE_WINDOW_MS` (WebSocket upgrades per client IP per window; empty keeps 60 and 60000 ms, `deploy/.env.example`). Every signed-in page load now opens a feed socket, so a site whose workstations share one egress IP may need a higher limit.
- Shutdown: on SIGTERM the server answers new submits `503 unavailable`, refuses new upgrades, waits up to 2 s for in-flight HTTP, stops dispatch intake, lets in-flight dispatch finish up to the latest outstanding source deadline plus 5 s, then closes sockets and the database. `stop_grace_period: 30s` in `deploy/compose.yml` is unchanged and covers the default 10 s source timeout. The ceiling for a site's largest `timeoutMs` is now 18 s (2 s + 18 s + 5 s = 25 s, 5 s inside the grace period); the M1 note said 20 s. A site above 18 s must raise `stop_grace_period` (not enforced; `docs/deploy.md`).
- The web app and API ship in one image behind the client update gate; no client minimum version change (ADR-0013: clients parse tolerantly, additive WebSocket changes need no bump).

## API and WebSocket contract changes
Reference: `docs/api.md`. No `api-breaking` PR merged since M1 (the last was #506); oasdiff reports nothing for this phase.

- `POST /queries`: the 202 is unchanged and stays the acknowledgment (FR-064). After the request, its parts, one `pending` row per source and the audit row are recorded, each source is queried in the background and settles once to `returned`, `failed`, `timedOut`, `credentialsMissing`, `credentialsRejected` or `interrupted`. The source's answer never rides in the 202. During a drain or after a fatal error a new submit is answered `503 unavailable` before anything is recorded; a retry that replays a recorded idempotency key still gets its stored 202.
- WebSocket `welcome.latestSeq` is live: the owner's newest `event_log` seq (0 when none), read at each `hello`. If the read fails the socket closes with 1011.
- WebSocket `sourceStatus` `{ seq, at, correlationId, partId, sourceId, resultId, status }` is live: published after each source outcome commits, to the owner's sockets only, and also written to `event_log`. Replay from `hello.lastSeq` is M2 P1.
- Close codes: 4001 (session ended) is the only contract code and the client signs out. 4000, 1001, 1008 and 1011 are server-local; every close other than 4001 means reconnect with backoff.
- `resultHidden` and `resync` joined the WebSocket schema (M2 P0, ADR-0013). Nothing sends them yet (M2 P1 and M3 P2).
- Planned routes with a merged contract and no handler (they answer 404 until M2 P1 and P2): `GET /queries`, `GET /queries/{correlationId}`, `GET /admin/audit`, `GET /admin/audit/export`, `GET /admin/queries/{correlationId}`.
- Audit: the outcome transaction writes a `sourceResponded` row with the requester's audit envelope, and the sweep writes `interrupted` rows. Audit rows are never deleted or rewritten.

## Known limits
- Mock sources only. Nothing reaches a real state or national system, and the prototype holds no real CJIS data.
- Status only: a settled source shows its status word, not its answer. Payloads, mapping, severity and the results view are M2 P1.
- No replay. A `sourceStatus` a client misses (socket down, restart) is lost until replay by `lastSeq` lands (M2 P1); no HTTP route returns per-source status yet. A row swept to `interrupted` is in the database and the audit log, but the screen shows it only once replay lands.
- Drain narrowing (#574): during the drain a refused enqueue after the request was recorded logs a warning only; the rows stay `pending` for the next start's sweep, that request's 202 is never delivered, and a retry with the same `Idempotency-Key` replays it. A submit already past the 503 check when a fatal hits outside the drain can trigger a second fatal, and `closeDb` under a hung outcome transaction can log a spurious fatal after a clean drain (no data lost). Spec 5.2 still says 20 s where `docs/deploy.md` says 18 s. #574 holds these and the other AW4 minors.
- `resultHidden`, `resync`, the five planned routes and `ackReceipt` metrics are contracts or accepted-and-ignored only.
- A session that expires while the feed socket is down gets a 401 on upgrade, which the browser reports as 1006 rather than 4001, so the feed retries (up to every 30 s) until the 15 s config refresh signs the user out (#66, M2 P1).
- #511 carries the remaining M1 carry-overs; P0.5 closes CFG-2, CFG-3, T27 IC1 and CV1, C-M-1, C-M-2 and the password minimum from it. CFG-4 moved to M2 P3.
- `config:validate --diff <tag>` is M2 P2; until then the config change against the last tag is the text diff of the resolved configs (empty for this phase).
