# M1 Forms and terminal

Date: 10-04-26

M1 exits on the front-end v1 demo (ADR-0011, ADR-0012): the dispatcher form and terminal, the officer screen, and the admin console (visual config builder, publish, history, users). A submit ends at the 202 acknowledgment. Dispatch, source answers and live per-source status are M2 P0.5 (see "Known limits").

## Config changes for site developers
Config schema stays at v1 (`CONFIG_SCHEMA_VERSION` 1); every change below is additive, so every M0 site file stays valid. `config:validate --diff <tag>` arrives in M2 P2, so the change against M0 is the text diff of the resolved configs (`git diff --no-index docs/releases/m0/default.resolved.txt docs/releases/m1/default.resolved.txt`, and the same for `example-ok`), summarised here.

```
ok packages/config/sites/default.json (6 warnings)
ok packages/config/sites/example-ok.json (7 warnings)
```

The warnings are all `config.conditionallyRequiredWithoutPosition`: a field a rule can make required (`plateType`, `make`, `caliber`, `description`, and in `example-ok` also `plateColor`) has no positional slot in the command that is shown, so a terminal user cannot fill it by position. They are warnings by design (the field is still reachable by keyword) and do not fail validation.

The resolved configs, verbatim as printed by `pnpm config:validate --resolved <file>` (JSON, kept as .txt so formatting never rewrites it): [`m1/default.resolved.txt`](m1/default.resolved.txt) and [`m1/example-ok.resolved.txt`](m1/example-ok.resolved.txt).

What changed against M0, in words:

- Feature flags: two new optional flags, `adminConfig` and `adminUsers` (ADR-0011). They gate the admin config routes and the user administration routes; a flag that is absent is off. `default.json` turns both on and `example-ok` inherits that through `extends`.
- Theme: `theme.defaultMode` accepts `"auto"` (ADR-0009, #304). A site that sets it must also set `theme.auto` to something other than `off` (`config.autoDefaultNeedsAuto`). `default.json` now ships `defaultMode: "auto"` with `auto: "os"`; M0 shipped `day` with `auto: "off"`.
- Defaults: `defaults.agency` is `EXAMPLEPD` in both sites (new key; `state` unchanged: `TX` and `OK`).
- New query type `DL` (driver licence), fields `licenseNumber`, `state`, `last`, `first`, `dob`, three rules, both mock sources selected, and an `alsoRun` of `WNT` mapped from `last`, `first`, `dob`. New commands `DL` (`licenseNumber`, `state`, `last`, `first`, `dob`), `NAM` (a second command for `PER`; `example-ok` orders its positions `last`, `first`, `race`, `sex`, `dob`) and `PROP` (a second command for `PRO`: `propertyType`, `serial`, `state`).
- `VEH` gains a `plateColor` field (picklist `plateColor`: `BK`, `WH`, `BL`) with a rule that shows it when the state differs from the site default; `example-ok` also requires it then. `PER` gains a `state` field and requires `dob` when the state differs from the site default.
- `PRO` gains an `expanded` section and the fields `state`, `make`, `model`, `caliber` and `agency`, with eight rules: `make` shows for firearm or electronics and is required for a firearm; `caliber` shows and is required for a firearm; `model` shows for electronics; `serial` is required for a vehicle or when the state differs from the default; `description` is required for an article.
- Picklists: `propertyType` gains `ELECTRONICS` and `VEHICLE`; new picklist `plateColor`.
- Keywords: `MISSING` (critical) and `RECOVERED` (info) join `STOLEN`, `WANTED`, `EXPIRED` and `NO RECORD`.
- Response mappings: summary mappings for `PER`, `PRO`, `WNT` and `DL` join `VEH`.
- Quick access: `WNT` and `DL` join `VEH`, `PER` and `PRO` (D-B15). `commands`, `sources`, `personas`, `auth`, `delegation`, `retention`, `locales` and the keyword severity styles are otherwise unchanged.
- Mock files (`packages/config/mock/default.json`, `example-ok.json`): hand-written canned responses for the new query types: `DL` (no-record default only), a `PRO` stolen-article scenario on serial `ZZSTOLEN1` and a `WNT` missing-person scenario on last name `MISSING`. They hold example values only and the mock adapter does not read them until M2 P0.5.

## Upgrade impact
- Migrations `0003` to `0008` (the API applies them at startup; take the usual backup first):
  - `0003_query_tables`: `query_request`, `request_key` (wrapped per-request keys, `values` and `payload` scopes) and `source_result` tables, with the idempotency unique index (per user, part 0) and the status check.
  - `0004_query_triggers`: `query_request` is insert-once (no update); `source_result` status is write-once from `pending`; `source_result` rows are never deleted.
  - `0005_query_no_replace`: no replace or duplicate insert on `query_request` and `source_result` (including a rowid reuse), an idempotency-key guard, `query_request` rows are never deleted, rowids stay positive.
  - `0006_query_origin`: `query_request.origin` must be `primary` or `alsoRun`.
  - `0007_site_config_version`: `site_config_version` table (draft, published, superseded) holding the live and draft site config, with one published row per site and triggers that keep history frozen, never deleted and never replaced.
  - `0008_config_superseded_frozen_must_change_password`: adds `user.must_change_password` (not null, default false) and tightens the config history trigger so a superseded version stays superseded.
- `ALLOW_MOCK_SOURCES` is unchanged: mock sources are still refused unless it is `true`.
- The live site config now lives in the database (ADR-0011). The first start after the upgrade seeds version 1 from the configured site file; from then on the stored version is the live source and the file is only compared, never used (the store logs when they differ). Change a deployed site through the admin console (draft, validate, publish, rollback), not by editing the file on the host. A store with versions but none published refuses to start.
- Mock files changed as listed above; nothing to regenerate by hand.
- `stop_grace_period: 30s` in `deploy/compose.yml` is unchanged and still covers the default 10 s source timeout; a site that raises any `timeoutMs` above 20 s must raise it too (not enforced; see `docs/deploy.md`). Nothing waits on a source until dispatch lands.
- The backup host now needs `rclone` 1.65 or newer: `scripts/ops/backup.sh` refuses an older one before it starts (Ubuntu's packaged 1.60 gets a 501 on its first PUT to R2). Replacement steps are in `docs/deploy.md` (#487).
- Users created in the admin console get a server-generated temporary password and must change it at first sign-in (see the contract section). Existing users are unaffected (`must_change_password` defaults to false).

## API and WebSocket contract changes
New under `/api/v1` since M0 (full reference in `docs/api.md`):

- `POST /queries`: submit a query. Needs `X-Requested-With`, `Idempotency-Key` and the `configHash` from `GET /config`. Answers `202` with `correlationId`, `acknowledgedAt` and one entry per part (the query is part 0, each nested "also run" query follows); `409 configHashMismatch` on a stale hash, `429` over 30 submits per user per minute. The 202 is the end of the submit in M1: the request, its parts and the audit row are recorded and nothing is sent to a source.
- Admin config, access `admin` or `implementer`, feature `adminConfig`: `GET /admin/config`, `PUT /admin/config/draft` (optimistic lock, `409 draftConflict`), `POST /admin/config/validate`, `POST /admin/config/publish`, `GET /admin/config/versions`, `POST /admin/config/versions/{version}/rollback`, `GET /admin/config/versions/{version}/export`. A publish reaches open dispatcher forms within 15 seconds (clients refetch `GET /config` on that interval and on focus).
- Admin users and sessions, access `admin`, feature `adminUsers`: `GET` and `POST /admin/users`, `POST /admin/users/{id}/disable`, `PUT /admin/users/{id}/role` (`409 lastAdmin`), `GET /admin/users/{id}/sessions`, `DELETE /admin/sessions/{sessionId}`. The temporary password is only in the 201 body of the create. The user list carries `signInCount`, `lastSignInAt` and `distinctIps` (a count, never an address).
- `403 passwordChangeRequired` on every `/api/v1/**` route and on the WebSocket upgrade for an account that still has its temporary password, until `POST /auth/change-password` succeeds (the same password is refused).
- Roles: `implementer` is new (config only; a submit by an implementer is `403 forbidden`).
- WebSocket: unchanged in M1 (`hello`, `welcome`, `ping`, `pong`; `ackReceipt` accepted and ignored). `welcome.latestSeq` is always 0 and `sourceStatus` is not published until M2 P0.5.

`api-breaking` PRs merged since the `m0` tag (09-28-26), each flagged by oasdiff as an enum value added to a response, which the contract check reports as an error; none removes or renames anything:

- #304 (09-29-26): `theme.defaultMode` in `GET /config` may be `"auto"` (ADR-0009). A client older than the release rejects it; web and API ship in one image behind the client update gate.
- #385 (09-29-26): the `ApiError` code enum gains `draftConflict` and `lastAdmin` (HTTP 409) for the admin console routes; existing routes never return them.
- #506 (10-03-26): the `ApiError` code enum gains `passwordChangeRequired` (403 on every session route while an admin-created user still has the temporary password). Clients should treat an unknown code as a generic failure and show the change-password form on this one.

#95 and #93 carry the label too but merged before the `m0` tag and are in the M0 notes.

## Known limits
- No query responses until M2 P0.5. A submit ends at the 202 acknowledgment: nothing is sent to a source, no source answers, and the acknowledgment never claims results.
- Submits made before M2 P0.5 keep `pending` source rows until the startup sweep lands (ADR-0012). The rows are never deleted, and a settled row is never rewritten.
- `sourceStatus` is not published and `welcome.latestSeq` is always 0 until `event_log` lands (M2 P0.5); replay by `lastSeq` follows with the feed (M2 P1).
- The auto-submit and settle path of A4 ("clean no-record") and smoke step 4 are part of the M2 P0.5 gate.
- #511 carries (M1 carry-overs: WebSocket receipt policy, key versioning, audit catalogue, admin UI). It is not closed by M1.
- The published image has no `org.opencontainers.image.revision` label, so the host cannot prove which commit it runs (found at the M1 restore and smoke run); a follow-up adds the label in the publish workflow.
- `config:validate --diff <tag>` is M2 P2; until then the config change against the last tag is the text diff of the resolved configs.
